# 由上而下解釋

使用者看過一遍的技術名詞很快就忘；先懂概念，才能快速做決定。所以解釋要從最高層開始，細節只在使用者需要時才往下給。

## 第一則回覆

只講最上面一層，短到可以一眼讀完：

1. **一句話結論**：這東西是什麼、為什麼存在或為什麼要改。用使用者已經懂的詞說，不用新名詞。
2. **對使用者的意義**：它影響使用者的哪個決定或目標（要不要合併、要不要在意、對他接下來的路線有沒有用）。不知道使用者的目標時，講它對誰有用、對誰沒用。
3. **最多兩三個重點**，每點一句。只放會改變判斷的東西。

第一則不要放：逐項表格、檔案路徑、欄位名稱、程式碼、審查意見全文、驗證步驟。一定要用某個術語時，第一次出現就用一句白話說它是什麼。

結尾給一行可以往下的方向，例如「要看每個工具怎麼判定，或這對外部對接的影響，再說」，讓使用者自己選要深入哪一支。

## 使用者追問時

- 只往下一層，只回答問的那一支。不要藉機把其他細節一起倒出來。
- 每一層仍然先給結論，再給支撐它的細節。
- 細節層才放表格、`file:line`、程式碼片段和範例。範例優先用使用者正在看的真實東西，不要用抽象例子。
- 使用者指定字數或格式時，照做，優先於這份 skill 的其他規則。

## 範例

使用者：「解釋這個 PR 的脈絡」，PR 是替 MCP 寫入工具補上 annotations。

不好的第一則：逐一列出六個工具的三個 hint 值表格、規格變更、審查意見、驗證結果。

好的第一則：

> 這個 PR 讓 data-os 的工具更誠實地告訴外部的 agent 程式「我會不會破壞資料、能不能安全重試」。之前沒說，對方只能當成最危險的情況，每次都停下來問人。
>
> 對你的意義：如果 data-os 之後要開放給外部廠商自己的 agent 對接，這讓他們的判斷更恰當；如果只給自家 data agent 用，影響很小，因為自家程式不看這些標記。不管哪種，真正的安全仍靠 data-os 伺服器端自己的檢查。
>
> 想看每個工具怎麼判定，或審查卡在哪裡，再跟我說。
